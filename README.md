# 五子棋（井字棋外观 · 网页版）

纯静态页面，无依赖、无构建、无服务端。**双击 `index.html` 即可开始**。

棋盘是一块放大的井字棋格子：**15×15 个格子**，双方轮流往**格子里**画 X / O，
不落在交叉点上。规则就是五子棋——横、竖、撇、捺任意方向先连成 5 个的获胜，X 先手。

整体是白色极简风：纯白棋盘 + 很轻的圆角投影，界面全是白卡片配浅灰描边，
全屏只有 X 的红、O 的蓝和五连的金三处上色。
棋盘自身的圆角和 SVG 外框的圆角都按 viewBox 单位给、由 `layout()` 一起换算成像素，
所以棋盘缩小时两层圆角始终同心。

## 三种模式

- **人机对战** — 三档棋力（简单 / 普通 / 困难），可选执 X 先手或执 O 后手。
- **双人对战** — 同一设备上两人轮流落子。
- **联机对战** — 纯前端 WebRTC 点对点，双方交换一次房号即可开局，不经过任何服务器。

## 功能一览

**对局**：点格子直接落子（鼠标悬停先给一个半透明的 X / O 预览），
最后一手有金框、对手下出四时状态栏变红并把你必须堵的点圈出来、终局五连整条高亮；
悔棋、认输、重新开始、翻转棋盘；右侧按坐标记谱（列 A~O × 行 1~15，天元写作 `H8`）。

**分析与评分**：实时胜率条 + 数值优势、整盘胜率走势曲线、
每一手的失误标记（`?!` 疑问手 / `?` 失误 / `??` 漏着）、终局百分制评分。

**其他**：落子音效（WebAudio 现场合成，不含任何音频文件）、复制棋谱到剪贴板、
棋力/执子/音效/翻转等设置记在 localStorage 里，下次打开还是上次的样子。

### 对话面板

**只有联机对战才有**，和对手实时聊天。回车发送，单条上限 200 字符，
本地还有 400ms 的连点保护。人机和双人模式不显示对话面板。

## 规则实现说明

- 15×15 = 225 个格子，`index = row * 15 + col`；`1` = X（先手），`-1` = O。
- 判胜只看穿过刚落那一子的四条线，不做全盘扫描——搜索里每生成一个着法都要判一次。
- **长连（六子以上）同样算赢**。自由规则五子棋没有禁手，黑棋的三三、四四、长连都不判负。
- 棋盘下满且没人连成五判和棋。

### 成五点

`winPoints(bd, side)` 返回"下在这里就能连成五"的全部空点。这是整个引擎最核心的一条信息：

- 非空 —— 该方下一步就赢；
- 长度 ≥ 2 —— 双四，对方只能堵一个，已经挡不住了。

能成五的点必定紧挨着自己的一颗子（一条五连里除它以外还有四颗，五格塞四子，
必有一颗与它相邻），所以先按邻子筛一遍再逐点试，不用 225 格全试。

## AI 设计

negamax + Alpha-Beta + 迭代加深，外加 PVS、LMR、null-move 剪枝和 Zobrist 置换表。
着法排序用 置换表着法 → killer → 落点启发（四方向连子数）→ history。
五子棋没有吃子，所以 null-move 是成立的——落子只会对自己有利，不存在 zugzwang。

### 三条五子棋特有的设计

**1. 强制着法先行。** 每个结点做的第一件事不是展开着法，而是问两个问题：

```
自己能成五吗？      -> 直接返回胜
对手有成五点吗？    -> 只有一个：这一步没得选，就堵那儿
                       有两个及以上：双四，返回负
```

这一条既是正确性保障，也砍掉了绝大部分分支——比任何剪枝都管用。
静态搜索（quiesce）也是同一套逻辑：五子棋没有吃子，但有完全等价的水平线效应，
搜索正好停在一个"对手已经有四"的局面上会以为还有救，所以把强制着法一直走完才评估。

**2. 候选点只取现有棋子周围 1~2 格。** 225 个空点全展开的话分支因子是 200 上下，
搜索深度会掉到 2 层。根结点和第一层用 radius 2（保留各种"跳"的形状），
再往下收窄到 radius 1。所有能立刻成五、能堵四的点都必然紧贴棋子，收窄一个都不会漏，
代价只是放弃"从两格开外另起炉灶"这种慢着。

实测两种取法对战力完全相同（12 局 6:6），收窄的那版快 35%、深两层。

**3. 静态评估建立在窗口表上。** 全盘共 572 条长度为 5 的线（横 165 + 竖 165 + 撇 121 + 捺 121）。
每条线数一数 X / O 各占几格，被一方独占才计分：

| 窗口里的子数 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 分值 | 1 | 14 | 160 | 2200 | 400000 |

再按"窗口中心离天元多远"加权（100 → 44）——边上的连子能延伸的方向少，
实战价值低得多。一个四（2200）远高于一条活三（约 490），因为四下一步就成五。

窗口表、每格属于哪些窗口都在启动时算好；落子时只更新穿过这一格的 20 个窗口，
**评估增量维护**，比每次全盘重算（572 窗口 × 5 格）快一个数量级。
成五点也直接靠增量维护的"每条线各有几个自己子"筛出来，不用逐格试下再判五。

### 开局库

`OPENING_BOOK` 是几条常见开局：天元起手，白棋贴角或直指，黑棋随之挂角。
好处是开局不至于走出莫名其妙的自损着法，而且同一局面有多个分支时会随机挑一个，
不会每盘棋都一模一样。库里的着法仍会用本地规则校验一遍，不合法就当没有。

### 棋力档位

`js/game.js` 的 `DIFFICULTY`。中局（双方各 8 子）10 次取样的实测：

| 档位 | 迭代上限 | 时间预算 | 随机余量 | 实测深度 | 实测耗时 |
|---|---|---|---|---|---|
| 简单 | 2 | 600ms | 500 | 2 | ~80ms，且在同分着法里随机挑，每盘不重样 |
| 普通 | 12 | 2000ms | 0 | 5.2 | ~1.5s |
| 困难 | 16 | 6000ms | 0 | 5.8 | ~2.7s（最慢 4.5s） |

迭代上限只是"别无限搜下去"的保险，实际层数由时间预算和"下一层搜不搜得完"
共同决定——所以同一档在空盘和乱战里挖到的深度并不一样。

困难档每步要想好几秒——这是有意的，它比另外两档强出一大截。

三档之间的对战力（同机自我对弈，双方交换先手）：

```
普通 vs 简单   8 : 0
困难 vs 普通   4 : 2
```

样本很小，只能说明档位顺序是对的。「困难」比「普通」强得有限——两者的搜索深度
（5.2 层 vs 5.8 层）本来就拉不开，多给的时间大半被指数级的分支因子吃掉了。
真正的差距体现在战术线上：多算一两层强制着法序列，就能多看见一步双四。

### AI 不占用主线程

搜索跑在 **Web Worker** 里，所以电脑思考时界面完全不卡：落子动画照常播放、按钮照常可点。
状态栏下方会实时显示电脑搜到的深度和结点数。

这里有个 `file://` 带来的约束：既不能用 `importScripts()` 加载本地脚本，
也不能 `fetch()` 读源码（真实用户的 Chrome 会以 CORS 拦掉）。
所以 `rules.js` 和 `ai.js` 都写成**具名工厂函数**，主线程把它们的源码
`toString()` 出来拼成一个 Blob 当 Worker 跑，main 线程和 Worker 共用同一份引擎代码。
Worker 万一创建失败或中途挂掉，会自动退回主线程继续算，不会让对局卡死。

棋子定位也从 `left/top` 改成了 `transform: translate()`——后者能交给合成层渲染，
主线程即使被占住，动画也不会僵在半路。

## 实时胜率与终局评分

胜率换算用 logistic：`胜率 = 1 / (1 + 10^(-评分差/1000))`。
系数 1000 是按五子棋的评分量级标定的——一条活三大约 500 分，也就是"领先一条活三"
约 76%，两条活三的优势约 91%，量级对得上。

对局结束后给出**评分（满分 100）**：

```
总分 = 结果分 + 质量分

结果分（0~50）   胜 50，和 25，负 0

质量分（0~50）   由平均每手损失(ACPL)换算：50 × exp(-ACPL / 400)

  每手损失 = 落子前局面对该方而言的价值 − 落子后的价值，只取非负部分。
  下出最优着法时约为 0，失误越大越高。
  除数 400 同样是按量级定的：随手放掉一条活三大约扣掉质量分的 71%。
```

等级：≥85 为 S·神级，≥70 为 A·优秀，≥55 为 B·良好，≥40 为 C·一般，其余 D·待提高。
面板同时列出结果分、质量分、平均每手损失、最大失误（含手数）和最长连子。
**人机对战只给玩家打分**，双人和联机模式两边都给。

同一套"每手损失"数据还驱动着胜率曲线图和棋谱里的失误标记。

评估跑在 Worker 里，用固定 4 层深度，不占用主线程。
忙不过来时会主动丢弃中间采样点，宁可评分少几个样本，也不让胜率条一直卡在旧值上。

**评估以"下一步该谁走"的视角去搜、再折算回 X 视角。** 五子棋里先手权很值钱，
固定让 X 先搜会让胜率条每隔一手就跳一下，出现锯齿。

## 联机对战

```
房主 创建房间  ->  房号 7K2MA  ->  告诉朋友
朋友 输入房号  ->  自动连接，房主执 X 先手
```

只要 **5 个字符**。要做到这一点必须有个中间人：WebRTC 的 DTLS 指纹由浏览器随机生成、
无法自定义或省略，光它就有 32 字节（base64 后 43 个字符），一条完整的连接信息最少约 100 字节，
5 个字符最多承载 30 bit，差了 25 倍以上。所以房号只是"房间名"，
真正的 offer/answer 通过**免费的公共 MQTT broker** 转发（默认 broker.emqx.io，
失败会自动依次尝试 hivemq、mosquitto）。

```
房主   订阅 room/a -> 生成 offer  -> retained 发布到 room/o
加入方 订阅 room/o -> 收到 retained 的 offer -> 应答 -> retained 发布到 room/a
房主   收到 answer -> setRemoteDescription -> 数据通道建立（此后点对点直连）
```

双方都先订阅再发布，配合 MQTT 的 retained 消息，加入方哪怕晚一步也能拿到 offer。
连上之后会把 retained 清掉，不给 broker 留垃圾。

MQTT 客户端是自己写的（只用到 CONNECT / SUBSCRIBE / PUBLISH-QoS0 / PING，
为此引一个上百 KB 的 CDN 库不划算），所以**没有任何前端依赖**。

**想自建 broker**：加个查询参数即可，多个用逗号分隔。

```
index.html?broker=ws://192.168.1.5:9001
```

仓库里带了一个能跑的最小 broker 和静态服务，方便自测：

```bash
bun test/mqtt-broker.js 9001      # 最小 MQTT broker
bun test/serve.js 0.0.0.0 8080    # 静态托管，局域网内可直接访问
```

注意 `file://` 被浏览器视为安全上下文，**会拦掉 `ws://` 的中转连接**（混合内容）。
所以本地用 `ws://` 自测时要用 `test/serve.js` 以 `http://` 打开；连公网 `wss://` 则不受影响。

防护措施：

- 每条落子消息带手数序号，对不上就提示局面可能已不一致。
- 收到的着法只校验"这一格是不是空的"，非法着法直接忽略。
- 收到的聊天文本走 `textContent` 写入，不经过 HTML 解析，天然免疫注入。
- 轮不到自己时不能操作，悔棋在联机模式下禁用。
- 断线、对方认输、再战（自动交换先后手）都有对应处理。

已知限制：

- **需要联网**，且依赖公共 broker 的可用性。
- 连接信息会经过第三方服务器。房号只有 5 位（32^5 ≈ 3300 万种），
  理论上有人盯着 broker 是可以撞上的。**别用它传敏感信息。**
- 只用了公共 STUN，没有 TURN。双方都在严格 NAT / 对称 NAT 后面时可能连不上。
- 房号没有占用检测：两个人恰好随机到同一个房号会串到一起（概率极低）。

## 测试

三套测试都是纯函数级别的，能在 bun 里直接跑，不需要浏览器。

`rules.js` 做的是全量校验：把棋盘上**全部 572 条可能的五连**一条一条摆出来，
逐条验证判胜（2860 次正例），再逐条拆掉任意一颗子换成对方棋子验证不判胜
（11440 次负例）。任何方向上的数数写错（边界、方向、起止）都会立刻在这组数字上暴露，
比零散单测硬得多。此外还覆盖长连、跳四、候选点半径与越界、
和棋判定、最长连子、坐标往返。

`ai.js` 覆盖两块最要紧的东西：

- **增量维护 vs 从零重算**。成五点用"每条线的子数"增量筛，静态评估用增量窗口分，
  两者都有对应的"从零算一遍"版本。400 个随机局面上逐个对照，必须逐位一致——
  这两块是搜索的地基，一旦算错，棋力会莫名其妙地掉而看不出原因。
- **战术**：自己有成五点必须成五、对手冲四/跳四/活三必须应对、
  有杀先杀不去补防、双四局面下仍给出合法着法。
- 还有速度、着法合法性，以及一局完整的自我对弈。

`online.js` 覆盖两块纯逻辑：房号生成与规范化（含全角折半角、长度、字符集、随机性），
以及自写 MQTT 客户端的编解码——剩余长度变长整数的边界值、各类报文的类型与标志位、
粘包/拆包/逐字节喂入、UTF-8 往返、空载荷（清除 retained 用）。

这套测试抓到过一个隐蔽问题：AI 的候选点生成用了带代次标记的临时数组来去重，
如果哪次忘了自增代次，连续两次调用会互相串味——单看棋力根本发现不了，
只有"连续调用互不干扰"这一条能测出来。

## 已知限制

- 只实现自由规则五子棋，**没有禁手判定**（黑棋的三三、四四、长连都不判负）。
- 未实现重复局面判和，超长对局需要手动重开。
- 联机模式没有悔棋协商机制（悔棋被禁用）。
- 没有对局回放/逐步复盘，错过的局面只能靠悔棋倒回去看。
